음수 인덱스를 찾았지만 이중 역참조에 막혔습니다. 순환 참조로 PIE를 구하고 OOB를 확장해 대회에서는 ROP로 해결했으며, 대회 후에는 FSOP로 다시 풀었습니다.

    자료 범위 2026년 11월 3일 문제 바이너리와 Dockerfile을 다시 확보했습니다. 당시 FSOP 풀이 코드와 함께 GitHub에 보관했으며, 복구 후 재실행 검증은 하지 않았습니다.

    상황과 처음 막힌 지점

    음수 인덱스로 범위를 벗어나는 접근을 찾았습니다. 하지만 포인터를 두 번 역참조하는 구조라 바로 libc 주소를 읽을 수 없었습니다. GDB 스크립트로 bss 주변 포인터를 조사했고, 바이너리 내부의 순환 참조를 이용해 PIE 기준 주소를 구했습니다.

    접근 범위를 넓힌 과정

    곱셈에서 유한한 double 두 값의 결과가 무한대로 넘어가는 경로를 확인했습니다. 1e308과 2를 넣는 것만으로는 calibrated() 검사를 통과하지 못했습니다. 충분한 메모리를 먼저 요청한 뒤 곱셈을 실행해야 접근 범위를 넓힐 수 있었습니다.

    # 원문 후속 코드의 메모리 요청 설정
N_MMAP, MMAP_CHUNK_SZ = 64, 0x800000
# 요청 크기 합계: 0x20000000 = 512 MiB
# 원문에서 설명한 calibrated 조건: 0x1fffffff 초과

    확장된 OOB로 stdout 관련 포인터를 채운 청크를 탐색해 libc 기준 주소를 구했습니다. 이후 같은 읽기·쓰기 조건에서 두 가지 풀이를 구성했습니다.

    대회 중 해결과 대회 후 풀이

    시점 사용한 경로와 결과
    대회 중 PIE → OOB 확장 → libc → environ → 스택
    main 반환 주소를 찾아 ROP 체인 구성. 한 문제 해결
    대회 후 쓰기 가능한 메모리에 fake FILE·wide_data·wide vtable 구성
    _IO_list_all을 연결하고 정상 종료 시 FSOP로 셸 획득

    다시 정리한 코드

    대회 당시 코드는 읽기 어려워 다시 작성했습니다. 메뉴 조작 함수와 주소 읽기·쓰기 함수를 분리하고, PIE 누출부터 FSOP 트리거까지 일곱 단계로 나눴습니다. 구조체 필드 오프셋도 이름 있는 상수로 옮겼습니다.

    def write_mem(addr, data):
    load(PTR_SLOT, p64(addr))
    load(slot_of(rw_base), data)
